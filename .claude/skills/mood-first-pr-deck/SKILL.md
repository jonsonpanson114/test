# 雰囲気から考える PR資料づくり

営業が「これを使いたい」とお客さんに思ってもらうための資料を、**社内資料の事実だけで**作る。
元になったのは、4人用ワークブース「IDO」のPR資料づくり。IDOでは付箋・ポラロイド・手書き風の資料になったが、それは**IDOのフライヤーが付箋をモチーフにしていたから**。別の製品を同じ見た目にしても意味がない（間仕切で同じことをして「そういうことじゃない」と言われた）。
持ち帰るべきは見た目ではなく、**進め方**：資料を読む → 雰囲気を言葉にする → それに合わせて構成とデザインを決める → 作る → 目で見て直す。

## 先に押さえる原則

1. **デザインは、その製品の資料から導く。** 表紙・色・書体・写真の撮り方・コピーの口調・図面の描き方、すべてが雰囲気の手がかり。使い回すのは「進め方」と「部品の作り方」まで。付箋・ポップ・雑誌風・図面風…は、雰囲気の答えの一例にすぎない（`references/mood-analysis.md`）。
2. **雰囲気は、まず言葉にして、短く見せて合意を取る。** いきなり全ページを作らず、「雰囲気メモ」＋表紙1枚＋中身1枚を見せる。方向が違えば、全ページを作る前に直せる。
3. **導入すると何が良くなるかから始める。** 仕様の説明より先に、お客さんの状況・悩み・得られる変化。見出しは、そのお客さん（設計者・施主・担当者）の言葉で。
4. **画像は、渡された資料のものだけ。** トリミングと拡大縮小まで。AIに描き直させると形・色・日本語が崩れる。自作してよいのは、アイコン・図面風の線画・模式図・背景。資料に無い写真は、枠（「写真：〇〇より」）にして、ダミー画像で埋めない。
5. **均等に並べすぎない。** 同じ大きさのカードを揃えると、どの雰囲気でも「PowerPointっぽい」見た目になる。大きさ・向き・余白・写真の使い方に抑揚をつける（やり方は雰囲気ごとに違う）。

## 進め方

### 1. 素材を読む
- 渡された資料を**全部読む**（PDFはページ指定で全ページ）。数値・条件・制約が詰まっている。
- 画像の抜き出し: `scripts/extract_images.sh <pdf> <outdir>`。一覧画像（`_sheet.jpg`）を**目で見て**、どれが何かを確認してから選ぶ。
- 写真かCGか、出典はどこか（ページ・カタログ版）をメモする。注記に使う。
- ファイルが大きくて取り込めないときは、**ユーザーに添付を頼む**（雰囲気は画像を見ないと読めない。文字だけから推測しない）。
- 元資料が【社外秘】なら、最後に公開可否の確認を促す。

### 2. 雰囲気メモを書く（`references/mood-analysis.md`）
キーワード3つ／色／書体の印象／コピーの口調／写真の扱い／避けること／読む人。これを数行で書き、見せて合意を取る。迷うなら、2〜3方向で表紙だけ作って見比べてもらう。

### 3. 構成を決める（1枚＝1メッセージ）
素材と読み手に合わせて決める。定番の流れ：表紙 → 悩み／課題 → 解決の全体像 → 選び方 → 機能・仕様 → 安心材料（性能値・法規）→ 事例 → 次の一歩。
**再構成**を頼まれたら、元の順番をなぞらない。読み手が「次に何を知りたいか」で並べ替え、重複は統合し、1ページ1メッセージに分ける。元資料にある良い構造（選定フローなど）は残す。

### 4. 作る
- `assets/template.html` は**部品の書き方の例**（付箋スタイル）。雰囲気が違うなら、CSSの部品は作り直す。スライドは `<section class="slide">`（1920×1080）、ページ番号は `.pg` を置くだけで自動採番、写真枠は `data-img` で後から差し替え。
- フォント: `scripts/setup_fonts.sh <dir>`（丸ゴシック・手書き風・Outfit・Noto Sans JP）。雰囲気に合う書体が別にあれば、それを取得する。
- 色は、製品の実物の色から1〜2色＋雰囲気が決めた補助色。増やしすぎない。

### 5. 見て直す（省かない）
`node scripts/render.js deck.html out --scale 1` でPNG化し、**全ページを画像として見る**。日本語の折り返し、重なり、はみ出し、帯の文字が隠れる、が出やすい。直して再レンダリング。複数ページは `montage` で一覧に。

### 6. 書き出す・渡す
- `node scripts/render.js deck.html out --scale 2 --pdf deck.pdf`（PNG 3840×2160、ベクターPDF）。複数HTMLを1冊にするなら `scripts/merge_pdfs.sh`。
- PDF・PNG・一覧画像・元のHTMLと素材を、同じフォルダに。
- 渡すときは `references/content-rules.md` の確認事項を、**「確認してほしいこと」として箇条書きで**。

## 内容を守るルール（詳細は references/content-rules.md）
- 数値・仕様は資料のまま。測定値は**条件（周波数・測定環境・参考値である旨）とセット**で。
- 「完全防音」「〜は不要」などの断定表現は使わない。法規は「〜に配慮した仕様」「要申請」「物件ごとに確認」。
- 資料に無いこと（自分で付けた名前・用途の提案・換算値・色の例）は、**資料に無い案**として最後に報告する。
- お客様向けの文面に「社内資料」「勉強会資料」を残さない。連絡先・担当者名は作らず、見える空欄にする。

## 使い方の例
- 「この仕様書とフライヤーからPR資料を作って」→ 1〜6を通しで。まず雰囲気メモ＋表紙＋中身1枚。
- 「この資料を、別の製品でも同じ考え方で作って」→ **見た目はコピーしない。** 新しい製品の資料から雰囲気メモを書き直す。
- 「もっと面白みを」→ 原則5に戻り、均等になっている箇所を探して、その雰囲気なりの抑揚をつける。
- 「事例・パターンを増やして」→ 写真を増やすのではなく、選べる仕様の組み合わせを描き起こす（`references/design-system.md` の「パターン集」）。
- 「別のテイストも見たい」と「同じテイストで中身を増やしたい」は別の依頼。**最初に確認する。**
